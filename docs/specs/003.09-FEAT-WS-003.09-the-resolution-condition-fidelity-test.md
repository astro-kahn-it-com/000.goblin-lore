### **I. FUNCTIONAL MANDATE**

**Strategic Goal** This feature implements a dedicated test confirming the
`**Resolution Condition:**` line extraction (`RESOLUTION_CONDITION_LINE` regex, per this project's
already-built `extract.ts`) preserves the exact showrunner-authored text — including punctuation,
capitalization, and any embedded markdown emphasis — with zero paraphrasing or truncation, across a
range of realistic condition-statement lengths and phrasings, including deliberately long or
structurally unusual boundary cases.

**Business Value**

- **Protects the one field in the entire schema this project deliberately kept purely
  human-authored:** Every other field in `SceneFrontmatterSchema` is either inferred from structure
  or mechanically derived — Resolution Condition is the single exception, explicitly designed to
  preserve a showrunner's exact narrative judgment rather than compress it into a structured field.
  This feature is what makes that design choice actually reliable.
- **Closes a specific, previously-identified risk:** This project's own earlier design discussion
  flagged that a long or punctuation-heavy Resolution Condition could silently truncate at an
  unexpected boundary given the current single-line regex extraction — this feature is the direct,
  deliberate test of exactly that risk.
- **Feeds the Reconciliation Protocol's substance-checking requirements:** The MS-06 Reconciliation
  Protocol's `revision_log` validation depends on being able to trust that a Resolution Condition
  (and similarly-structured free-text fields) survive extraction intact — this feature is the proof
  that trust is warranted for at least this one field.

**Failure Criteria (Rollback Plan)**

- **Immediate Rollback:** If any tested Resolution Condition — short, long, or containing an
  embedded colon or other regex-adjacent character — is extracted with any alteration (truncation,
  paraphrasing, whitespace mangling) from its original authored text.
- **Suspension:** If a genuinely unresolvable extraction ambiguity is found (e.g., a Resolution
  Condition the showrunner wrote across multiple lines, which the current single-line regex cannot
  correctly capture at all) — pause and determine whether the outline format itself needs a
  multi-line-capable convention for this field, rather than attempting to force a fix onto an
  inherently single-line-only regex.
- **Kill Switch:** None — a discovered truncation bug is fixable in the extraction regex; standard
  remediation applies, though with elevated priority given this field's unique,
  deliberately-human-authored status.

---

### **II. TECHNICAL CONSTRAINTS & REQUIREMENTS**

- **Boundary Case Coverage:** Test cases include a short, simple condition; a long, multi-clause
  condition; a condition containing an embedded colon (a regex-adjacent character given the field's
  own `**Resolution Condition:**` label syntax); and a condition containing markdown emphasis
  (`*italic*` or `**bold**` text within the condition itself).
- **Exact-Match Assertion:** Each test asserts character-for-character equality between the authored
  text and the extracted `resolution_condition` field value — not a fuzzy or normalized comparison
  that could mask subtle whitespace or punctuation drift.
- **Multi-Line Limitation Documentation:** If the current single-line regex is confirmed incapable
  of correctly handling a multi-line Resolution Condition, this is explicitly documented as a known
  format constraint (a showrunner must keep this field to one line), not silently left as an
  undiscovered failure mode.
