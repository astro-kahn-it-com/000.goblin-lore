---

### **I. FUNCTIONAL MANDATE**

**Strategic Goal** This feature implements the automated test suite proving `002-POL-02` (the
Residue Mandate) is actually upheld by every implemented release mechanic, not merely documented as
policy. It runs every mechanic — Near Miss, Relational Catharsis, and any future addition — against
a known starting ledger state and asserts the post-release state is never byte-identical to a
fully-reset baseline, per-field, not just via a single summary flag.

**Business Value**

- **Converts a policy statement into an enforced, CI-blocking guarantee:** `002-POL-02` exists as
  governing text, but text alone cannot prevent a future contributor from accidentally implementing
  a residue-free release mechanic under deadline pressure — this feature is the actual enforcement
  mechanism.
- **Makes negative-space testing (proving something did NOT happen) rigorous rather than
  superficial:** "This value is never fully reset" is inherently harder to test comprehensively than
  a positive assertion — this feature's per-field, per-mechanic enumeration closes the gap a single
  top-level check would leave open.
- **Is explicitly extensible to future mechanics:** As the simulation's release-mechanic vocabulary
  grows beyond Near Miss and Relational Catharsis, this suite's structure is the template every new
  mechanic must be added to before it can be considered complete.

**Failure Criteria (Rollback Plan)**

- **Immediate Rollback:** If any currently-implemented release mechanic (Near Miss, Relational
  Catharsis) fails its non-baseline assertion — this indicates a genuine Residue Mandate violation
  that must be fixed in the mechanic itself, not in this test suite.
- **Suspension:** If a new release mechanic is merged without a corresponding addition to this suite
  — pause and treat the missing coverage as a blocking gap, since an untested mechanic could
  silently violate the Mandate without detection.
- **Kill Switch:** If this suite itself is found to have been silently weakened (a per-field
  assertion replaced with a single summary-flag check that could pass despite a genuine per-field
  violation) — treat as a Sev-1 process failure; escalate to Lead Architect within 4 hours.

---

### **II. TECHNICAL CONSTRAINTS & REQUIREMENTS**

- **Per-Field Enumeration:** For each release mechanic, the suite enumerates every ledger field that
  mechanic is documented to touch (per each mechanic's own Feature deliverables) and asserts
  non-baseline state for each field independently — not a single aggregate "is this different"
  check.
- **Mechanic Registry:** A central, explicit list of "currently covered release mechanics" is
  maintained alongside the suite; any mechanic not on this list is flagged by a meta-test as a
  coverage gap.
- **Baseline Definition:** "Baseline" for each field is explicitly defined per field type (e.g.,
  resentment's baseline is `0`; a flag's baseline is `false`/`null`) — the suite does not infer
  baseline generically.
