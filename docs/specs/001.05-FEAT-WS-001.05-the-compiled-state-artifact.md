### **I. FUNCTIONAL MANDATE**

**Strategic Goal** This feature implements the deterministic serialization of every corpus file that
passed Pass 1 and Pass 2 validation into a single `goblin-bible/compiled/bible-state.json`,
structured for efficient downstream consumption — indexed by character ID, grievance ID, and
location ID, not a flat, unordered dump. Two compiler runs against an unchanged corpus must produce
byte-identical output, which requires deliberate, explicit key-ordering discipline rather than
reliance on incidental JavaScript object serialization behavior.

**Business Value**

- **Makes the compiled state genuinely reproducible:** Byte-identical output across runs is the
  literal prerequisite for the Initiative's Sovereign Objective — without this feature,
  "deterministic" is an aspiration, not a property anyone has verified.
- **Gives `worker-sower` an efficient consumption structure:** Index-based lookup (by
  character/grievance/location ID) means the Terminal OS's boot sequence and selection lottery never
  need to linearly scan the full corpus at runtime.
- **Enables trustworthy diffing:** A structured, deterministically-ordered artifact is what makes
  the MS-03 Ledger Diff Tool's byte-level divergence reporting actually meaningful, rather than
  noisy with incidental ordering differences.

**Failure Criteria (Rollback Plan)**

- **Immediate Rollback:** If two consecutive compiler runs against an identical corpus produce a
  non-identical `bible-state.json` (any byte divergence) — this is a direct violation of the
  feature's core purpose and blocks release immediately.
- **Suspension:** If the indexed structure's construction time exceeds the corpus-scale compute
  budget defined in the governing Initiative — pause further index-structure complexity growth
  pending a performance review.
- **Kill Switch:** If a downstream consumer (`worker-sower`) is found to depend on non-indexed,
  flat-dump-style access patterns that the indexed structure cannot support without a breaking
  redesign — escalate to Lead Architect for a schema-compatibility review within 24 hours.

---

### **II. TECHNICAL CONSTRAINTS & REQUIREMENTS**

- **Deterministic Key Ordering:** All object keys in the output JSON are explicitly sorted
  (alphabetically, by declared field order, or another deterministic rule) at serialization time —
  the implementation must never rely on V8's incidental object-key insertion-order behavior as its
  determinism guarantee.
- **Index Structure:** The compiled artifact's top level is partitioned into `characters`,
  `grievances`, `locations`, `possessions` sub-objects, each keyed by the entity's own `id` field
  for O(1) downstream lookup.
- **Atomic Write:** The compiler writes to a temporary file and performs an atomic rename to
  `bible-state.json` on success, so a crash mid-write can never leave a partially-written, corrupted
  compiled artifact on disk.
- **Version Stamping:** The compiled artifact includes a `compiledAt` ISO 8601 timestamp and a
  `corpusHash` (SHA-256 of the concatenated, sorted source file contents) for downstream provenance
  tracking.

- [ ] **[TASK-01] Index Structure Specification:** Design the exact nested shape of
      `bible-state.json`, including the `characters`/`grievances`/`locations`/`possessions`
      partitioning and per-entity field ordering rule. | **Est:** 2h | **Owner:** Lead Architect
- [ ] **[TASK-02] Determinism Strategy:** Specify the exact key-sorting algorithm (e.g.,
      `Object.keys(obj).sort()` applied recursively before `JSON.stringify`) that will be used
      throughout serialization. | **Est:** 2h | **Owner:** Lead Architect

**Phase 2: Implementation** _(Total: 10h)_

- [ ] **[TASK-03] Implement the Deterministic Serializer:** Build `serialize.ts` per
      TASK-01/TASK-02, recursively sorting keys before final `JSON.stringify`. | **Est:** 4h |
      **Owner:** Backend Lead
- [ ] **[TASK-04] Implement the Atomic Write:** Build `atomicWrite.ts` using a temp-file-then-rename
      pattern. | **Est:** 3h | **Owner:** Backend Lead
- [ ] **[TASK-05] Implement Version Stamping:** Add `compiledAt` and `corpusHash` computation to the
      serialization pipeline. | **Est:** 3h | **Owner:** Backend Lead

**Phase 3: Validation** _(Total: 7h)_

- [ ] **[TASK-06] Byte-Identical Reproducibility Test:** Run the compiler twice against an unchanged
      corpus fixture; `diff` the two outputs; confirm zero divergence. Repeat 10 times. | **Est:**
      3h | **Owner:** QA Lead
- [ ] **[TASK-07] Atomic Write Crash Simulation:** Kill the compiler process mid-write (via a test
      harness injecting a delay and `SIGKILL`); confirm no partial `bible-state.json` exists
      afterward and the prior valid artifact (if any) remains intact. | **Est:** 3h | **Owner:** QA
      Lead
- [ ] **[TASK-08] Index Lookup Performance Check:** Confirm `characters['bog']`-style lookup against
      the compiled artifact resolves in O(1), not by linear scan, via a benchmark comparing lookup
      time at 4 vs. 400 simulated characters. | **Est:** 1h | **Owner:** QA Lead
